Common concepts of interface types:**

- FMI Application Programming Interface (C)
    
    - All required computations are triggered by calling standardized C functions from the importer into the FMU
    - FMU can signal certain events back to the importer using callback functions provided by the importer
    - Usage of C: most portable programming language
- FMI Describtion Schema (XML):
    
    - Schema defines the structure and content of a model description file (modelDescription.xml) generated by a model environment
    - XML file contains the definition of all exposed variables, their interdependencies (model structure) and capability flags of the FMU
    - C-API allows to access and store the variable definitions (without memory or performance impact) in its own representation
- FMU distribution (ZIP)
    
    - FMU is distributed as one ZIP file
    - FMI modelDescription.xml
    - binaries and libraries required to execute the FMI functions (.dll or .so files)
    - and/or the sources of the FMI functions
    - documentation, and other data used by the FMU (e.g., tables or maps).

**2.1 Mathematical Notation**

- Mathematical description of
    
    - ODEs in state-space representation with discontinuities (events)
    - Algebraic system equations
    - discrete-time equations (sampled-data systems)
- FMU and imporrter uses variables to exchange information (described in modelDescription.xml)
    
    - Access to variables via appropriate API functions
- **Super-dense time:** [image]
    
    - real part of tuple is the independent variable of the FMU for describing the continuous-time behavior of the model beteween events
    - integer part t_I = 0 during continuous integration
        
        - Is a counter to enumerate and sistinguish the events at the same continuous time instant t_R
    - lexicographical ordering

**Example:**

- Assume that an FMU has an event at t_R = 2.1 s
- Variable changes discontinuously
- If no event iteratio occurs, the time instant when the event occurs is defined as (2.1, 0)
- The time instant when the integration is restarted is defined as (2.1, 1)
- Hybrid differential equations exposed by FMI for Model Exchange or wrapped by FMI for Co-Simulation are described as piecewise continuous-time systems
- Discontinuities can occur at time instants t0, t1, ..., tn where ti < t_i+1
- Time instants are called events:
    
    - time events: are known beforehand
    - state events and step events: are defined implicitly
- Variables between events are either continuous or do not change their value
- Discrete time variable: changes its value only at events
- Continuous variables: only floating point values

**Advancing Time in Co-Simulation**

- Time advances (possibly variable) steps negotiated between the co-simulation algorithm of the importer and the FMU
- Importer calls fmi3doStep with the currentCommunicationPoint and a target communicatioStepSize (>0.0)
- During fmi3DoStep importer and FMU might encounter events (or other situations) that require reduction of the communicationStepSize (potentially even down to 0.0)
- FMU may use the return argument earlyReturnRequested of the callback fmi3IntermediateUpadeteCallback to signal the FMU to return early from the current fmi3doStep
- Output argument lastSuccessfulTime of fmi3DoStep allows the FMU to signal the importer its current internal time

**Variables**

- FMU and importers use variables to exchange information
- all variables are listed in modelDescription.xml
- Variables are identified with a uique handle calles value reference

- variables except Clocks, may be scalar or multi-dimensional arrays, Clocks must always be scalar

**Getting and Setting the Complete FMU State**

- For variabl step-size control of co-simulation algorithms: get the FMU state for every accepted comminucaition step
    
    - if the follow-up step is not accepted, restart co-simulation from this FMU state
- FMU state can be serialized and copied by a byte-vector
    
    - used to perform expensive steady-state initialization
    - copy the received FMU state in a by vector and store this vector on file
    - Whenever needed the byte vector can be loaded from file and deserialized
    - simulation can be restarted from this FMU state

**Dependencies of Variables**

Dependencies between variables of an FMU:

- allow the detection and classification of algebraic loops across inputs and outputs when connecting FMUs
- declare the relationship between derivatives and continuous states and other variables
- associate event indicators with variables
- defie the sparseness when computing partial derivatives, avoiding unnecessary calls

Dpendencies are encoded in the model description with the element structure and:

- do not resolve to dependencies of individual array elements
- do not take changing dependencies due to resizing of arrays via structureal parameters into account
- are independent of the FMUs current operating point and parameter settings
- FMU can indicate via a flag that it is able to provide detailed dependency information at runtime

 **Algebraic Loops**

- When connecting FMUs, loop structures may occur that lead to linear or nonlinear algebraic systems of equations
    
    - involving continuous and discrete time vraiables
- information about which output directly depends on which input us needed to detect and solve such systems of equations efficiently
- Data may be provided in the model structure
- Worst case: all output variables depend algebraically on all input variables
- loop may be solved iteratively (e.g., Newton Method)
- In every iteration variable s is provided by the solver
- residual is computed and used by the solver to determine a neew value of s as input of u of M4
- the iteration is terminated when the residual is small enough
- Works for initialization Mode, Event Mode, and Continuous-Time Mode

**State Machine and Semantics**

- State machines are used to define allowed calling sequences of FMI function
- Each state of the state machine corresponds to a certain phase of a simulation
- Each state description lists the governing equations and actions and the corresponding API functions influencing these equations in a table (not defining the calling order)
    
    - lists the allowed function calls and usage restrictions
- State machine defines the formal behavior of an FMU as it progresses zhrough different stages of its lifecycle
- Ensures consistent interaction between a master algorithm and FMUs during co-simulation or model exchange
- FMU behaves like a finite state machine, with well defined states and legal transitions.

**FMI Description Schema**

- static information related to the core functionality of the FMU
- Fmu variables and their attributes
- Optional information about the graphical representation and grouping of FMU variables into terminals
- Build information for source code FMUs is provided together with build description
- Not allowed to change the model description file (has to be consistent with the binary or source code implementations)
- Capability flags describe which optional functionalities the FMU supports
- Importers must be prepared to ignore unknown capability flags
- exporters must not generate capability flags without an XML namespace
- units for variables can be defined
    
    - allow automatic unit check  and value conversion in the importer to bridge the gap between FMUs from different simulation domains
    - all units can be defined as combinations if the 7 base SI units
    - definition consists of the exponent of the seven SI base units
    - Unit check when connecting variables of different FMUs
    - Dimensional analysis of equations
    - Unit propagation of unit definitions are missing for variables

- Model variables:
    
    - static information of all exposed variables
    - except for Clocks, variable elements can represent an arry variable
    - variable can have any number of alias element that define a variable alias
    - Causality:
        
        - parameter: value is provided by the importer or user (can be changed independently)
        - calculatedParameter: data value that is constant during the simulation and is computed during initialization
        - input: variable value my be used by the importer (forwarded to another FMU into this input)
        - output: variable value may be used by the importer (value can be forwarded to an input of another FMU, algebraic dependencies to the inputs may be defined via the dependencies attribute
        - local: local variables (continuous states, continuous states derivatives, clocked states, event indicators, initial unknowns, internal and intermediate variables)
        - independent: usually time, exactly one variable of an FMU must be defined as independent
        - structural parameter: variable value can only be changed in the configuration or reconfiguration mode
        - default causality: local (continuous state or event indicator must have causality local or output)
    - Variability:
        
        - defines the time instants when a variable may be changed by the importer or may change its value due to FMU internal computations depending on their causality
        - constant: value never changes
        - fixed: value is fixed in super state Initialized, does not change after initialization
        - tunable: value is constant between events and communcication points
        - discrete:
            
            - ME: value of the variable may change only in Event Mode
            - CS: if event mode is used, the value of the variable may only change in event mode. If event mode is not used, the value may change at communication points and the FMU must detect and handle such events internally
            - SE: value may change only at communication points
        - continuous: only real valued variables
- Model Structure
    
    - defines thedependencies between variables
    - required part of the model structure for all FMI types define the orderingof outputs and unknowns during initialization
        
        - ME FMU must also expose all derivatives of continuous states in the continuousStateDerivatives and all event indicators
    - optional part defines in chich way derivatives, outputs, and initial unnkown depend on inputs and/or parameters, and continuous-time states
    - listed dependencies declare the dependencies between whole (multi-dimensional-)variables and not individual elements of the variables

**4 FMI for Co-Simulation**

- In contrast to FMI for model exchange, a Co-Simulation implements not only the model algorithm, but also the required solution method
- Data exchange between FMUs is restricted to discrete communication points t_i (unless intermediate Update Mode is used)
- In the time between two communication points (or between entering Intermediate Update Mode), the subsystem inside an FMU is solved independently by internal means
- This leads to a delay for information "travelling through" the FMU
    
    - there cannot be an immeadiate reaction (direct feed-through) as in Initialization Mode, Event Mode or Continuous-Time Mode of Model Exchange
- Co-Simulation algorithm of the importer controls the data exchange and the synchronization between FMUs
- Co-Simulation algorithm is responsible for:
    
    - advancing the overall simulation time
    - exchange input and output data
    - triggering of input clocks
    - handling events
- Co-simulation algorithm is shielded from how the FMU advances in time internally
    
    - Example: FMUs containing ODEs and implementing FMI Co-Simulation require an ODE solver indide the FMU to internally advance time between the communication points
    - Example: FMUs representing controller code, an internal scheduling algorithm can trigger computations at th correcttime and order while advancing time to the next communication point

**Co-Simulation enbales the folowing features:**

- variable or constant communication step size h_i
- reject, repeat communication steps, e.g., with reduced communication step size or a different set of input values
- update inputs and retrieve outputs at intermediate points within a communication step
- return early from fmi3DoStep because of an event influencing the environment was detected by the FMU
- dedicated initialization mode, which allows computation of consistent initial condition over algebraic loops
- handling of Clocks and events
- ability of the FMU to provide derivatives of outputs w.r.t. time, to allow approximation techniques
- ability of the FMU to provide directional and adjoint derivatives
- supported flags are definied by capability flags

**4.1 Concepts**

4.1.1 Somoothness, Continuity and Discontinuity

- Inputs are set at specific communication point by the importer
- FMU must make assumptions about the values between these communication points including points of intermediate updates
- Between communication points, even in Intermediate Update Mode, all changes must be assumed to be continuous
- Changes to continuous variables are only considered discrete in Event Mode
- If a contuinuous input changes discontinuously, the co-simulation algorithm of the importer must raise an event if supported to indicate to the FMU a discontinuous change of a continuous input
- Discrete inputs keep their values between communication points
    
    - changing discrete variables at communication points will likely require special handling within the FMU

4.1.2 Getting Derivatives of continuous outputs

- the n-th derivatives w.r.t. time of continuous outputs may be retrieved with fmi3GetOutputDerivatives
    
    - to allow interpolation / extrapolation of connected input variables between communication points by the importer
    - capability of derivatives is given by capability flag
- returned vales correspond to the derivatives at the current time of the FMU

4.1.3 Early Return

- A Co-Simulation is allowed to stop the execution of fmi3DoStep and return without reaching the predefined communication time
    
    - currentCommunicationPoint + communicationStepSize
- Early return can be used to shorten a communication step because of
    
    - an event happened inside the FMU which influences its outputs non-continuously
    - importer requests the stop of the current communication step in Intermeidate Update Mode
        
        - Example: importer wants to stop a communication step bacause other parts of the simulation indicate the necessity
    - FMU requests an additional communication point
        
        -  Example: FMU wants to communicate extreme of outputs to prevent model inconsitencies like negative pressure values caused by extrapolation of inputs
- Capability flag describes if the FMU supports early return after Intermediate Update Mode if requested by the importer
- Argument earlyReturnAllowd of fmi3InstantiateCoSimulation signals to the FMU if the importer allows early return

4.2.2 State: Intermdeiate Update Mode:

- can be only entered by the FMU itself using the callback function
- an FMU may enter Intermediate Update Mode in order to exchange input and output values between communication points
- Intermediate Update Mode allows the importer to request an early return from the current fmi3DoStep because of an event between communication points
- Importer cannot request entering Intermediate Update Mode from the FMU and hence for some use cases the importer relies on the callbacks from the FMUs

Intermediate Update Mode enables:

- advanced Co-Simulation with interpolation/extrapolation techniques of inputs and outputs (such as polynominal extrapolatio, Transmission Line Modeling (TLM) co-simulation, anto-alias filtering, smoothing of input
- the same input approximation that was possible in FMI 2.0 with fmi2setInputDerivatives, by evaluation of the apporximation polynominal by the importer and not within the FMU as in FMI2.0

- FMU signals support of Intermediate Update Mode via capability flag
- Co-simulation algorithm signals the support for Intermediate Update Mode by providing a non-Null callback function pointer for intermediateUpdate
- Intermediate values for continuous inputs are computed by the importer by an extrapolation polynominal build with the output derivatives of connected FMUs
- recommededIntermediateInputSmoothness: signals that the best convergence rates can be achieved if these approximation function are of smoothness C^k
- Importer must ensure that the input approximation function u_u is consitent with the values of the input variable
- Due to the way the internal solver may estimate and correct the approximation error, tentative states may occur and lead to tentaitive intermediate output values
- if an FMU internal integration step has been completed successfully, the importer can forward intermediate outputs to other FMUs where they can be used to approximate inputs
