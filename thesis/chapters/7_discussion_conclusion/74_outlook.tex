\section{Outlook and Future Work}
\label{sec:discussion_outlook}

Future work should first extend the master algorithms with adaptive and error-controlled macro stepping.
Local communication-step error estimates provide a theoretical basis for such control, but they must account for the direct-feedthrough structure of the coupled system and for the internal integration errors of the heterogeneous backends~\cite{arnold_error_2013}.
Such an extension requires rollback-aware step rejection and clear fallback rules for backends that cannot restore arbitrary past states.
Hybrid event handling should also use an exact physical-time representation.
An integer-based time base would make event ordering independent of floating-point comparisons.

Algorithmic scalability should be improved in two places.
The algebraic-loop solver could reuse Jacobians when the local loop structure is constant.
The execution layer could evaluate independent execution generations in parallel.
A systematic benchmark suite should include larger component graphs, different coupling densities, and different backend costs.
This would clarify when orchestration overhead dominates and when high-fidelity model switching provides the largest benefit.

The backend integrations can be broadened as well.
FMI~3.0 concepts such as clocks and scheduled execution are relevant for sampled and event-driven co-simulation workflows.
Supporting these features would improve the treatment of hybrid and discrete-time components beyond the FMI~2.0 Co-Simulation capabilities used in this thesis.
The OpenSim and FEM integrations could also be generalized.
In particular, a reusable FEM backend wrapper would separate NGSolve-specific model code from the common co-simulation interface more clearly.

Another extension is hardware-in-the-loop simulation.
In such a workflow, one simulated component is replaced by a physical device that exchanges signals with the remaining simulation in real time.
This use case would add requirements that are not addressed by the present framework.
The master algorithm would require bounded execution time, deterministic scheduling, real-time communication interfaces, and defined behavior for missed deadlines.
These requirements are especially relevant when a controller, actuator, or sensor is connected as physical hardware while the surrounding plant remains simulated.

A future comparison could rebuild the \ac{FMU}-only controlled-pendulum baseline in CoFMPy.
This would allow a direct comparison of trajectory agreement, runtime, and available master algorithms.
A second step could test whether CoFMPy's Python \ac{FMU} proxy can represent the OpenSim and \ac{FEM} pendulum wrappers.
The comparison would clarify which workflow parts are covered by an \ac{FMI}-centered Digital-Twin framework and which parts need heterogeneous hybrid orchestration.

Finally, the framework should provide stronger user-facing diagnostics.
Structural-analysis metadata, algebraic-loop blocks, event traces, switching decisions, and benchmark measurements are already available internally.
A reporting layer could expose this information for inspection, reproduction, and debugging of larger heterogeneous simulations.
