\section{Tool Comparison and Selection}
\label{sec:tool_selection}

The external tools used in this thesis were selected from the requirements derived in Section~\ref{sec:req_general_modeling} through Section~\ref{sec:req_interaction}.
The selection covers tools that were considered as realistic candidates for integration into \syssimx{}.
For each modeling domain, the chosen tool is justified by the required capabilities, the integration effort, and the scope of the thesis.

Each subsection follows the same structure.
It states the capability requirements and names the selected tool.
It then lists the alternatives that were rejected and the remaining limitations.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsection{Equation-Based Modeling}
\label{sec:tool_equation_based}

The equation-based modeling capability is required by UR-05.
The selected tool had to support declarative multi-domain physical modeling and hierarchical composition.
It also had to export simulation units through an FMI-compatible interface so that they can be loaded from the Python environment in which \syssimx{} is implemented.
The acausal multi-domain paradigm and the tool landscape are described in Section~\ref{sec:intro_sota} and Section~\ref{sec:241_modeling_equation_based}.

\paragraph{Selected tool.}
Modelica with the OpenModelica toolchain was selected on these grounds.
Modelica realizes the acausal multi-domain formalism of Section~\ref{sec:241_modeling_equation_based}.
OpenModelica provides an open-source compiler and FMI~2.0 Co-Simulation export.
Both are scriptable from Python, which makes integration into \syssimx{} direct.
The exported FMUs are loaded into \syssimx{} through the \texttt{FMPy} library described in Section~\ref{sec:tool_fmpy}.

\paragraph{Alternatives considered.}
Simulink and Simscape were considered and rejected.
Simulink is a signal-based block environment.
It does not match the acausal physical-modeling paradigm required for the considered subsystems~\cite{noauthor_simulink_nodate}.
Simscape adds acausal physical components on top of Simulink.
It remains embedded in the proprietary MATLAB ecosystem and requires explicit interface blocks between physical networks and signal-based control models~\cite{noauthor_simscape_nodate}.
This conflicts with the open and scriptable workflow targeted by this thesis.

\paragraph{Limitation.}
\syssimx{} cannot execute Modelica source models directly.
The OpenModelica toolchain is required as a separate step to translate them into FMI~2.0 Co-Simulation FMUs.

\subsection{FMU Import in Python}
\label{sec:tool_fmpy}

The FMU import capability supports the equation-based modeling workflow of UR-05 and the corresponding FMU wrapper requirement SR-05-01.
The selected library had to load FMI~2.0 Co-Simulation FMUs from Python, expose the model description, instantiate FMU slaves, read and write variables, and advance the FMU through the standardized co-simulation calls.
It also had to leave the system-level orchestration to \syssimx{}, because execution order, algebraic-loop handling, event handling, and runtime model switching are framework responsibilities.

\paragraph{Selected tool.}
FMPy was selected as the Python FMU importer~\cite{dassault_systemes__catia-systems_fmpy_2026}.
It supports loading, inspecting, validating, and simulating FMUs directly from Python.
For \syssimx{}, the important feature is its direct access to the FMI~2.0 model description and to the instantiated \texttt{FMU2Slave} object.
This allows the framework to derive ports and parameters from FMU metadata while keeping the master algorithms inside \syssimx{}.

\paragraph{Alternatives considered.}
PyFMI, CoFMPy, OMSimulator, and INTO-CPS Maestro were considered.
PyFMI provides a mature Python interface for FMI-based simulation and is often used together with Assimulo~\cite{andersson_pyfmi_nodate}.
Its focus is simulation of FMU-based models, whereas this thesis needs a lightweight importer that can be embedded below the \syssimx{} component abstraction.
CoFMPy targets rapid prototyping of FMI-based Digital Twins and combines FMU co-simulation with coordination, communication, storage, and Python-native extensions~\cite{friedrich_cofmpy_2025}.
This is broader than the importer role required here.
OMSimulator and Maestro provide stronger FMI-based orchestration environments with support for composite co-simulation scenarios~\cite{noauthor_omsimulator_nodate,thule_maestro_2019}.
Using either as the main execution backend would move orchestration out of \syssimx{} and weaken the framework contribution of this thesis.

\paragraph{Limitation.}
\texttt{FMPy} is used only as an FMU access layer.
It does not provide the architectural concepts required by \syssimx{}, such as typed framework ports, structural metadata, unified handling of non-FMU components, hybrid event orchestration, or runtime model switching.
These responsibilities are implemented in the framework itself.

\subsection{Musculoskeletal Modeling}
\label{sec:tool_musculoskeletal}

The musculoskeletal modeling capability is required by UR-06.
The selected tool had to support articulated biomechanical models with joints, constraints, and muscle or ideal actuators.
It also had to provide forward dynamic simulation and be accessible from the Python environment in which \syssimx{} is implemented.
The modeling approach and the runtime architecture of such tools are described in Section~\ref{sec:intro_sota} and Section~\ref{sec:242_modeling_musculoskeletal}.

\paragraph{Selected tool.}
OpenSim was selected on these grounds~\cite{OpenSim_Delp,seth_opensim_2018}.
It satisfies the capability requirements through its Simbody-based multibody engine and its biomechanical component library.
It also offers a native Python interface, which permits direct integration into \syssimx{} without an intermediate proprietary execution environment.

\paragraph{Alternatives considered.}
The AnyBody Modeling System and MuJoCo were considered and rejected.
AnyBody is a commercial biomechanics environment built around the AnyScript modeling language~\cite{damsgaard_analysis_2006}.
Its proprietary licensing and AnyScript-based authoring conflict with the open and scriptable Python workflow targeted by this thesis.
MuJoCo is a multibody physics simulator that has gained traction in biomechanics through extensions~\cite{todorov_mujoco_2012}.
Its native support for muscle-tendon actuation and standard biomechanical model libraries is less mature than that of OpenSim.
A systematic comparison across the wider landscape of musculoskeletal environments was outside the scope of this thesis.

\paragraph{Limitation.}
OpenSim does not provide native FMI export.
The framework therefore wraps OpenSim through a backend-specific component rather than through the generic FMU wrapper used for Modelica-based simulation units.

\subsection{Finite Element Modeling}
\label{sec:tool_fem}

The finite element modeling capability is required by UR-07.
The selected tool had to support spatially discretized continuum-mechanical models with programmable material laws and boundary conditions.
It also had to expose direct Python access so that models can be assembled, stepped, and queried from the \syssimx{} runtime.
The continuum-mechanical formulation and the role of the finite element library are described in Section~\ref{sec:intro_sota} and Section~\ref{sec:243_modeling_fem}.

\paragraph{Selected tool.}
Netgen/NGSolve was selected on these grounds~\cite{schoberl_c11_nodate,schoberl_netgen_1997}.
NGSolve exposes the finite element problem definition directly through a Python interface.
The user can configure spaces, weak forms, boundary conditions, and solver options programmatically.
This level of access allows the model to be wrapped as a co-simulation component and coupled to equation-based and musculoskeletal simulation units through a common contract.

\paragraph{Alternatives considered.}
CalculiX, FEBio, and openCFS were considered and rejected.
CalculiX is an open-source ABAQUS-compatible solver driven through input files~\cite{noauthor_calculix_nodate}.
Its file-based execution model conflicts with programmatic Python access at runtime.
FEBio is focused on biomechanics and soft-tissue mechanics~\cite{maas_febio_2012}.
Its Python interface is less mature than that of NGSolve for general continuum-mechanical models.
openCFS targets coupled multi-physics through standalone analysis runs~\cite{schoder_opencfs_2025}.
Its workflow is oriented at offline simulation rather than embedded runtime use.

\paragraph{Limitation.}
NGSolve has no graphical model-authoring front-end.
Geometry, material laws, boundary conditions, and weak forms must be defined programmatically in Python.
This requires the user to be familiar with the weak-form formulation of finite element models.
This limitation is acceptable because this thesis targets programmatic integration rather than interactive model authoring.

\subsection{Selected Toolchain}
\label{sec:tool_selection_summary}

The selected toolchain covers the four external capabilities required by the framework.
OpenModelica provides the equation-based model source and FMI export.
\texttt{FMPy} provides the Python access layer for exported FMUs.
OpenSim and Netgen/NGSolve provide the non-FMI backends for musculoskeletal and finite element models.
This split keeps the orchestration responsibility inside \syssimx{} while relying on established tools for the individual modeling domains.
