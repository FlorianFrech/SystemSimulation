\section{Tool Comparison and Selection}

The external tools used in this thesis were selected based on the requirements derived in the previous section. 
The comparison is therefore not intended as a comprehensive survey of all available modeling and simulation environments.
Instead, it focuses on those tools that were relevant for the required workflow and that were considered realistic candidates for integration into \emph{SysSimX}.
For each modeling domain, the selected tool is justified with respect to the required capabilities, the integration effort, and the overall scope of the thesis.

\subsection{Equation-Based Modeling}

For the equation-based part of the workflow, the selected tool had to support declarative multi-domain physical modeling, hierarchical composition, and export to a co-simulation-ready interface so that the resulting simulation unit can be consumed through the component abstractions of \syssimx{}.
The paradigm and the tool landscape are described in Sections~\ref{sec:intro_sota} and~\ref{sec:241_modeling_equation_based} and are not repeated here.

\emph{Modelica} with the \emph{OpenModelica} toolchain was selected on these grounds.
Modelica realizes the acausal multi-domain formalism introduced in Section~\ref{sec:241_modeling_equation_based}, OpenModelica provides an open-source compiler and FMI~2.0 Co-Simulation export, and both are scriptable from the Python environment in which \syssimx{} is implemented.

Simulink and Simscape were considered as alternatives and rejected.
Simulink is a signal-based block environment and therefore does not match the acausal physical-modeling paradigm required for the considered subsystems~\cite{noauthor_simulink_nodate}.
Simscape adds acausal physical components on top of Simulink but remains embedded in the proprietary MATLAB ecosystem and requires explicit interface blocks between physical networks and signal-based control models~\cite{noauthor_simscape_nodate}, which conflicts with the open, scriptable workflow targeted by this thesis.

\subsection{Musculoskeletal Modeling}

For the musculoskeletal part of the workflow, the selected tool had to support articulated biomechanical models with joints, constraints, and muscle or ideal actuators, provide forward dynamic simulation, and be accessible from the Python environment in which \syssimx{} is implemented.
The modeling approach and the runtime architecture of such tools are described in Sections~\ref{sec:intro_sota} and~\ref{sec:242_modeling_musculoskeletal} and are not repeated here.

\emph{OpenSim} was selected on these grounds~\cite{OpenSim_Delp,seth_opensim_2018}.
It satisfies the capability requirements stated above through its Simbody-based multibody engine and its biomechanical component library, and it offers a Python interface that permits direct integration into \syssimx{} without an intermediate proprietary execution environment.
Other musculoskeletal modeling environments, both research-oriented and commercial, exist and may be equally suitable from a purely biomechanical point of view.
A systematic comparison across such environments was outside the scope of this thesis, which targets heterogeneous system integration rather than a benchmark of musculoskeletal tools.
The selection therefore rests on the combination of domain capability, open-source availability, and practical integrability into the Python-based framework, rather than on a quantitative ranking.


\subsection{Finite Element Modeling}

For the finite element part of the workflow, the selected tool had to support spatially discretized continuum-mechanical models, programmable definition of material laws and boundary conditions, and direct Python access so that the model can be assembled, stepped, and queried from within the \syssimx{} runtime.
The continuum-mechanical formulation and the role of the finite element library as its computational back-end are described in Sections~\ref{sec:intro_sota} and~\ref{sec:243_modeling_fem} and are not repeated here.

\emph{Netgen/NGSolve}~\cite{schoberl_c11_nodate,schoberl_netgen_1997} was selected on these grounds.
It exposes finite element spaces, weak forms, boundary conditions, grid functions, and solver configuration directly through a Python interface, which allows the model to be wrapped as a co-simulation component and coupled to equation-based and musculoskeletal simulation units through a common contract.

Other open-source finite element environments were considered at a high level.
CalculiX~\cite{noauthor_calculix_nodate}, FEBio~\cite{maas_febio_2012}, and openCFS~\cite{schoder_opencfs_2025} were assessed as less direct candidates for a Python-centered prototype workflow, primarily because of less mature programmatic interfaces or a stronger orientation towards file-based pre-processing and execution.
A systematic benchmark of finite element tools was outside the scope of this thesis, which targets framework integration rather than a comparison of finite element platforms.

The chosen tool has one acknowledged limitation.
NGSolve requires a comparatively strong mathematical understanding of finite element modeling, since many aspects of the model are defined directly in code rather than through a graphical front-end.
This limitation is acceptable for the present work because the thesis focuses on controllable programmatic access and integration rather than on interactive finite element model authoring.

The selected toolchain therefore combines Modelica/OpenModelica, OpenSim, and Netgen/NGSolve, each chosen because it satisfies the domain-specific requirements while remaining accessible for integration into the Python-based workflow of \syssimx{}.
No single existing environment covered the full combination of heterogeneous model integration, hybrid co-simulation, and unified orchestration required for this work, which motivates the development of the framework presented in the following chapters.
