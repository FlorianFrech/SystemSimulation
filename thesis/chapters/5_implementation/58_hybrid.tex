\section{Hybrid Co-Simulation Algorithm}
\label{sec:impl_hybrid}

The hybrid co-simulation implementation realizes \ref{req:SR-10-04} under \ref{req:UR-10}.
It extends continuous macro-step execution with event detection, event localization, rollback, and event dispatch.
The theoretical concepts are introduced in Section~\ref{sec:236_cosim_hybrid}.
The implementation is provided by \texttt{HybridAlgorithm}.
Between events, it reuses the Gauss--Seidel execution path described in Section~\ref{sec:impl_algorithms_gs}.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsection{Scope and Component Contract}
\label{sec:impl_hybrid_scope}

Hybrid execution is activated during \texttt{System.initialize(t0)}.
The system classifies the registered components into event sources, event listeners, and continuous-only components.
If at least one event source is present, the selected continuous algorithm is replaced by \texttt{HybridAlgorithm}.

The component contract for event sources, listeners, rollback, and dense time is defined in Section~\ref{sec:architecture_system_connections}.
The \texttt{HybridAlgorithm} class uses this contract to detect and dispatch events during one macro interval.

Table~\ref{tab:hybrid_component_contract} summarizes the hybrid-specific operations used by \texttt{HybridAlgorithm}.
The general component interface is described in Section~\ref{sec:impl_component_interface}.

Event routing is stored on the \texttt{System}.

The route is stored in the system-level event-target map.
The hybrid algorithm uses this map when localized events are dispatched.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsection{Hybrid Macro-Step Sequence}
\label{sec:impl_hybrid_macro_step}

The entry point of the hybrid algorithm is \texttt{step(system, t, dt)}.
The method receives the macro interval $[t, t+\Delta t]$ and stores its current boundaries as \texttt{t\_left} and \texttt{t\_right}.
The algorithm processes the remaining interval \texttt{[t\_left, t\_right]} in a while loop.
This is necessary because an event may split one macro step into several accepted continuous substeps.
After an event has been localized and handled, \texttt{t\_left} is advanced to the handled event time and the remaining part of the interval is processed in the next loop pass.
Figure~\ref{fig:impl_hybrid_macro_step} summarizes one pass through this loop.

\begin{figure}[t]
    \centering
    \includegraphics[width=1\linewidth]{diagrams/out/pdf/execution/hybrid/Hybrid_Step.pdf}
    \caption[Macro-step sequence of the hybrid co-simulation algorithm]{Macro-step sequence of the hybrid co-simulation algorithm.
    The algorithm prepares inputs, tests the current interval for events, localizes the first crossing, and dispatches cascaded events in dense time.}
    \label{fig:impl_hybrid_macro_step}
\end{figure}

For the current left boundary \texttt{t\_left}, \texttt{\_prepare\_inputs()} first stages all signal inputs in generation order.
The same pass resolves algebraic loops with the local SCC solver from Section~\ref{sec:impl_algebraic_loops}.
The algorithm then checks all event sources for crossings in the remaining interval \texttt{[t\_left, t\_right]}.
The trial-step procedure is described in Section~\ref{sec:impl_hybrid_detection}.

If no crossing is detected, the remaining interval is accepted as a continuous co-simulation step.
The algorithm delegates this step to \texttt{GaussSeidelAlgorithm.step(system, t\_left, t\_right - t\_left)} and returns.
Thus, the hybrid path follows the Gauss--Seidel behavior whenever no event splits the macro interval.

If a crossing is detected, the algorithm first localizes the event time inside the current interval.
The coupled system is then advanced only up to this event time.
The localized events are recorded with their \texttt{DenseTime} stamps and dispatched to the subscribed listeners.

Event handlers may change component states and trigger further events at the same physical time.
The algorithm therefore prepares the inputs again and repeats event handling until no pending event remains.
After this dense-time loop has terminated, the remaining part of the original macro interval is processed in the next pass.
Sections~\ref{sec:impl_hybrid_detection}, \ref{sec:impl_hybrid_localization}, and~\ref{sec:impl_hybrid_handling} describe detection, localization, and dense-time handling.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsection{Event Detection via Trial Stepping}
\label{sec:impl_hybrid_detection}

Event detection is implemented in \texttt{\_detect\_crossings()}.
The method checks all event sources over the current interval \texttt{[t\_left, t\_right]}.
For each source, it stores a rollback snapshot and caches the current input values.
It then evaluates the event indicators at \texttt{t\_left}, advances the source in a trial step to \texttt{t\_right}, and evaluates the indicators again.

The left and right indicator values are passed to \texttt{detect\_event\_crossings()}.
This method applies the crossing directions registered with the corresponding \texttt{EventIndicator} objects.
In the same pass, the algorithm collects optional \texttt{InternalEventInfo} hints reported by the source.

The trial step is not accepted as part of the simulation state.
After the indicator values and internal hints have been collected, the source is restored to its snapshot at \texttt{t\_left}.
The method returns the rollback data, the left-boundary indicator values, the detected event names, and the retained internal hints.
These data are consumed by the event localization step in Section~\ref{sec:impl_hybrid_localization}.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsection{Event Time Localization}
\label{sec:impl_hybrid_localization}

If at least one crossing was detected, \texttt{\_locate\_event\_time()} searches for the earliest event time in the current interval.
The method starts from \texttt{[t\_left, t\_right]} and optionally narrows this interval with internal event hints.
Such hints are reported by components with internal micro-stepping and provide a smaller bracket for the event.

The remaining search is performed by bisection.
At each midpoint, the event sources are restored to the left boundary, advanced to the candidate time, and evaluated again.
The algorithm keeps the half interval that still contains a crossing.
The search stops when the time interval is below \texttt{tol\_time} or an indicator value satisfies \texttt{tol\_value}.

After localization, the algorithm evaluates the event sources at the located time and collects the active events.
It then restores every event source to \texttt{t\_left}.
The accepted advance to the event time is therefore still performed by the macro-step sequence.
Detection and localization do not change the simulation state.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsection{Event Handling at Dense Time}
\label{sec:impl_hybrid_handling}

After localization, the accepted system state is still at \texttt{t\_left}.
The hybrid algorithm therefore advances the coupled system to \texttt{t\_event} with \pyfn{GaussSeidelAlgorithm.step(system, t\_left, t\_event - t\_left)}.
This is the same continuous stepping path that is used when no event is present.
Only the step length is shortened.

Before event handlers are executed, the algorithm removes duplicate events.
It keeps a cache of events that have already been handled during the current macro step.
An event is skipped when the same component and event name were handled less than \texttt{event\_dedup\_tol} earlier.
This avoids repeated handling of the same crossing near event boundaries.

Event handling is performed in an inner dense-time loop.
Each pass handles all pending events at the current \texttt{DenseTime}.
The algorithm records the events and evaluates the indicators before dispatch.
It then dispatches the subscribed handlers, prepares inputs again, and evaluates the indicators after handling.
New indicator crossings create cascaded events at the same physical time with an increased microstep index.
The loop terminates when no new event remains.
The limit \texttt{max\_microsteps} prevents an infinite cascade.

The \texttt{handle\_events()} method groups pending events by listener component.
If one listener receives multiple events at the same dense time, their handlers must commute.
The algorithm first checks optional \texttt{event\_commutativity} annotations.
If no annotation is available, it evaluates all handler orders from the same rollback state.
The resulting states are compared with \texttt{\_states\_equal()}.
A non-commutative event set raises a \texttt{RuntimeError}.
Commutative events are dispatched through \texttt{System.dispatch\_event()}.

After the dense-time loop has terminated, the algorithm prepares the inputs once more.
It then moves \texttt{t\_left} to \texttt{t\_event + tol\_time}.
This small offset prevents the same crossing from being detected again immediately.
The outer loop then continues with the remaining interval \texttt{[t\_left, t\_right]}.

\subsection{Verification}

The verification uses three small scenarios that isolate hybrid features not covered by the case study.
The scenarios test cascaded events at one physical time, simultaneous events on one listener, and events that occur strictly inside a macro interval.

\paragraph{Event chain and superdense time.}
The first scenario verifies cascaded event handling at one physical time.
A \texttt{HybridSource} with $x_{\mathrm{src}}(t) = -\tfrac{2}{3} + 2t$ crosses zero at the analytical time $t_e = \tfrac{1}{3}\,$s.
This event is routed to a \texttt{HybridCombi}, which doubles its velocity from $-1\, \frac{\mathrm{m}}{\mathrm{s}}$ to $-2\, \frac{\mathrm{m}}{\mathrm{s}}$.
The velocity change triggers a second event on the \texttt{HybridCombi}.
This second event is routed to a \texttt{HybridListener}, which inverts its velocity from $+3\, \frac{\mathrm{m}}{\mathrm{s}}$ to $-3\, \frac{\mathrm{m}}{\mathrm{s}}$.
The expected result is therefore one event at $(t_e,0)$ and one cascaded event at $(t_e,1)$.

    The annotations show the emitted and received events.}
    \label{fig:impl_hybrid_verification_chain}
\end{figure}

Figure~\ref{fig:impl_hybrid_verification_chain} shows the three component trajectories and the localized event time.
The algorithm detects the source crossing in the macro interval $[0.30,0.35]\, \mathrm{s}$.
It locates the event at $t_e \approx 0.33333359\, \mathrm{s}$.
The first handler runs at microstep~$0$.
The cascaded event is then detected and handled at microstep~$1$.
The post-event slopes match the expected dynamics with $v_{\mathrm{combi}}=-2\, \frac{\mathrm{m}}{\mathrm{s}}$ and $v_{\mathrm{lis}}=-3\, \frac{\mathrm{m}}{\mathrm{s}}$.
The absolute error against $t_e = \tfrac{1}{3}\, \mathrm{s}$ is about $2.6\cdot 10^{-7}\, \mathrm{s}$.

\paragraph{Strong event simultaneity and commutativity.}
The second scenario verifies simultaneous events that target the same listener.
Two \texttt{HybridSource} components are configured to cross zero at $t_e = \tfrac{2}{3}\, \mathrm{s}$.
The first source uses $x_1(t)=\tfrac{2}{3}-t$ with falling-edge detection.
The second source uses $x_2(t)=-\tfrac{2}{3}+t$ with rising-edge detection.

Both events are routed to one \texttt{HybridListener}.
The listener starts with velocity $v_0=3.0\, \frac{\mathrm{m}}{\mathrm{s}}$ and applies the updates $v \mapsto -v$ and $v \mapsto 2v$.
These updates commute.
The expected post-event velocity is therefore $-2v_0=-6.0\, \frac{\mathrm{m}}{\mathrm{s}}$.

Figure~\ref{fig:impl_hybrid_verification_simultaneity} shows the two source indicators and the listener trajectory.
The algorithm detects both crossings in the macro interval $[0.65,0.70]\, \mathrm{s}$.
It localizes them at the dense time $(t_e,0)$ with $t_e \approx 0.66666667\, \mathrm{s}$    .
The listener trajectory changes slope at this time and matches the expected post-event velocity.

Listing~\ref{lst:hybrid_simultaneity_log} confirms the dispatch path.
Both events are grouped on the \texttt{Listener}.
Because the listener does not provide a commutativity annotation, the dynamic check is used.
The check confirms identical final states for both handler orders before the events are dispatched.

\paragraph{Internal event reporting.}
The third scenario verifies event hints from a component with internal micro-stepping.
An \texttt{EventReportingComponent} uses the indicator
\[
    h(t) = (t - T_1)(t - T_2)
\]
with roots $T_1 = 0.45\,$s and $T_2 = 0.55\,$s.
The macro step size is $\Delta t = 0.2\,$s, so both roots lie inside the interval $[0.4,0.6]\,$s.
At the two macro endpoints the indicator has the same sign.
Endpoint-based trial stepping would therefore miss both events.

The component steps internally with $\Delta t_{\mathrm{int}} = 0.01\,$s.
Whenever the indicator changes sign between two internal steps, it reports an \texttt{InternalEventInfo} bracket.
In this scenario the reported brackets are $[0.44,0.45]\,$s and $[0.54,0.55]\,$s.
An \texttt{EventListener} subscribes to the event and inverts its slope whenever an event is handled.

Figure~\ref{fig:impl_hybrid_verification_internal} shows the indicator and the listener trajectory.
The first hint narrows the bisection to $[0.44, 0.45]\,$s and locates the event at $t = 0.45\,$s.
The handler inverts the listener slope.
The second hint then narrows to $[0.54, 0.55]\,$s and locates the event at $t = 0.55\,$s.
Both located times match the analytical roots within machine precision.

After the second event, the algorithm detects a residual crossing in the remaining interval.
This crossing refers to the event that was already handled at $t=0.55\,$s.
The per-step deduplication cache rejects it because the time difference is below \texttt{event\_dedup\_tol}.

These scenarios verify the event orchestration of the hybrid master algorithm for localized, simultaneous, and internally reported events.
