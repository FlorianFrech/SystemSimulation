\section{Structural Analysis and Execution Ordering}
\label{sec:impl_structural}

This section describes the implementation of the structural analysis introduced in Section~\ref{sec:233_cosim_structural_analysis}.
The implementation realizes SR-10-02 and SR-10-03 under UR-10, and SR-11-02 under UR-11.
It derives persistent graph metadata from the registered components, signal connections, and direct-feedthrough information.
This metadata is later consumed by coupled initialization and by the master algorithms.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsection{Inputs, Outputs, and Stored Metadata}
\label{sec:impl_structural_inputs}

Structural analysis depends only on the registered system structure of the \texttt{System}, namely the components, the signal connections, and the per-component direct-feedthrough metadata.
In addition, the analysis derives the set of \emph{active outputs} from the connection list.
These are the output ports referenced by at least one outgoing signal connection.

All results of the structural analysis are stored directly on the \texttt{System} instance so that the master algorithms and the initialization loop can read them without recomputation.
Table~\ref{tab:structural_metadata} lists the stored fields, the routine that produces them, and their purpose.

\subsection{Graph Construction and Loop Detection}
\label{sec:impl_structural_graph}

Graph construction is performed by \texttt{build\_graphs()}.
The routine clears previously cached structural metadata and adds every registered component as a node of both \texttt{graph} and \texttt{\_dag}.
Thus, isolated components remain visible even if they have no signal connections.
It then derives the set of active outputs from the connection list.
The final pass over the registered connections builds the full connection graph, the zero-delay graph, and the input lookup maps.

\paragraph{Full Connection Graph.}
The fourth step iterates over all signal connections.
Every connection is added to \texttt{graph} as an annotated multi-edge whose \texttt{src\_port} and \texttt{dst\_port} attributes identify the connected ports.
The same pass fills the input-lookup maps listed in Table~\ref{tab:structural_metadata}, so that downstream routines can resolve the driver of any input port without traversing the graph.

\paragraph{Zero-Delay Graph and Active-Output Filter.}
Execution ordering depends only on instantaneous dependencies, so \texttt{\_dag} contains only those signal connections that contribute to direct feedthrough.
A connection from component $A$ to component $B$ is inserted only if the destination port of $B$ influences at least one active output of $B$ according to \pyfn{direct\_feedthrough}.
Unlike \texttt{graph}, the zero-delay graph is a \texttt{DiGraph}, so parallel component-level edges collapse to one edge.
This active-output filter is the main difference between the \syssimx{} implementation graph and the conceptual graph of Section~\ref{sec:233_cosim_structural_analysis}.
In the worked example, the edge into component~D is removed because D exposes no direct feedthrough.
The edge from D to A is also removed because A exposes no direct feedthrough.
Component~D therefore remains an isolated node in \texttt{\_dag}.

\paragraph{Algebraic Loop Detection.}
Once the zero-delay graph has been assembled, \texttt{build\_graphs()} identifies the subsets of components that participate in an instantaneous cyclic dependency.
Section~\ref{sec:233_cosim_structural_analysis} has already established that each such subset corresponds to a strongly connected component of the zero-delay graph.
This implementation reuses that result directly through \pyfn{networkx.strongly\_connected\_components()}, which returns every maximal strongly connected subset of \texttt{\_dag}.

\paragraph{Multi-Component Loops.}
Any strongly connected component with more than one node is stored as an algebraic loop in the attribute \texttt{algebraic\_loops}.
The dashed red boundary in Figure~\ref{fig:struct_worked_b2} encloses the single multi-component SCC of the worked scenario and becomes the only entry of \texttt{algebraic\_loops}.
Each entry is a list of component names that collectively form one loop block.
The ordering inside a block is not semantically relevant at this stage, because the IJCSA solver of Section~\ref{sec:impl_algebraic_loops} treats the block as an unordered set of unknowns and equations.

\paragraph{Self-Loops.}
A one-component algebraic loop arises when an outer connection feeds an active output of a component back into one of its own direct-feedthrough inputs.
Such a configuration produces a self-loop in \texttt{\_dag} that the SCC pass alone cannot distinguish from an ordinary one-element component.
A second pass therefore iterates over all nodes and appends every node carrying a self-loop edge as a singleton entry of \texttt{algebraic\_loops}.
This unified representation realizes SR-11-02 and lets the IJCSA solver apply the same iteration scheme to multi-component and one-component loops.

\subsection{Execution Order}
\label{sec:impl_structural_condensation}

The zero-delay graph may contain directed cycles, so a topological sort cannot be applied to it directly.
Section~\ref{sec:233_cosim_structural_analysis} has shown that collapsing every strongly connected component into a single node yields the condensed graph, which is acyclic by construction.
The routine \texttt{compute\_execution\_order()} implements this idea on \texttt{\_dag} and then derives the generation-based schedule that the master algorithms consume.

\paragraph{Condensation.}
The condensation is obtained through \texttt{networkx.condensation()}.
The result is a directed acyclic graph whose nodes are identifiers of the strongly connected components of \texttt{\_dag} and whose edges reflect the inter-component dependencies that survive the collapse.
Figure~\ref{fig:struct_worked_d} shows the resulting condensed graph and the corresponding \texttt{execution\_order} before delayed-producer post-processing.
The mapping from component names to condensation identifiers is stored in \texttt{\_scc\_index} so that the initialization loop and the IJCSA solver can locate the loop block of any component in constant time.

\paragraph{Topological Generations.}
The acyclic condensed graph is passed to \pyfn{networkx.topological\_generations()}, which returns an ordered sequence of sets of condensation nodes.
Each set defines one \emph{generation} in the sense of Section~\ref{sec:233_cosim_structural_analysis}.
\syssimx{} then expands each condensation node to its component names, sorts them alphabetically, and stores the resulting list of lists in \texttt{execution\_order}.
A generation therefore contains either mutually independent components or the members of one algebraic loop.
In the same pass, \syssimx{} also builds \texttt{execution\_idx}, which maps each component name to its generation index.

\paragraph{Delayed Producer Post-Processing.}
The condensed schedule captures all instantaneous ordering constraints.
Components that are isolated in \texttt{\_dag} may still influence the coupled part of the system through delayed paths in \texttt{graph}.
\syssimx{} classifies such components as delayed producers and moves them to a final generation.
The predicate \texttt{is\_delayed\_producer()} checks whether a component has no incident zero-delay edges but can still reach a component with zero-delay structure through the full graph.
After relocation, \texttt{execution\_idx} is rebuilt so that the lookup remains consistent with \texttt{execution\_order}.
This relocation is a \syssimx{} scheduling choice.

\paragraph{Consumers of Structural Metadata.}
The metadata produced by \texttt{build\_graphs()} and \pyfn{compute\_execution\_order()} is computed once during \texttt{initialize(t0)}.
It is then consumed read-only by initialization and by the master algorithms.
They traverse \texttt{execution\_order}, use \texttt{\_input\_sources} for input propagation, and use \texttt{algebraic\_loops} to identify loop blocks for the IJCSA solver of Section~\ref{sec:impl_algebraic_loops}.

The Graphviz-based system graph visualizer consumes the same metadata.
It renders component groups, port labels, signal connections, event connections, execution-order indices, and algebraic-loop edges.
The visualizer supports UR-12 as an inspection helper.
It is not part of the simulation semantics.

\subsection{Verification}
\label{sec:impl_structural_verification}

The structural-analysis verification uses the four-component scenario of Figure~\ref{fig:struct_worked}.
The scenario is small enough to inspect manually, but it exercises the complete metadata path from registered connections to the final execution order.
The expected full connection graph contains all registered signal connections.
The expected zero-delay graph contains only the instantaneous dependencies induced by the direct-feedthrough maps of components~B and~C.
Components~A and~D expose no direct feedthrough and therefore do not contribute zero-delay edges.

Table~\ref{tab:structural_verification} summarizes the expected and observed metadata.
The result confirms that \texttt{build\_graphs()} preserves the full connection structure in \texttt{graph}, filters the zero-delay structure into \texttt{\_dag}, and detects the SCC formed by components~B and~C.
The subsequent call to \pyfn{compute\_execution\_order()} condenses this SCC into one generation and moves component~D to the final generation as a delayed producer.
