\subsection{FMI 2.0 Co-Simulation Wrapper}
\label{sec:impl_fmu}

This subsection describes the \texttt{FMUComponent} wrapper.
It realizes SR-03-01 by mapping FMI~2.0 Co-Simulation FMUs to the \texttt{CoSimComponent} interface of Section~\ref{sec:impl_component_interface}.
The wrapper delegates FMI calls to \texttt{fmpy}~\cite{dassault_systemes__catia-systems_fmpy_2026}.
It derives ports, parameters, value references, and direct-feedthrough metadata from the FMU's \texttt{modelDescription.xml}.

As described in Section~\ref{sec:cosim_fmi}, a Co-Simulation FMU keeps its own solver.
The wrapper therefore does not re-implement FMU simulation logic.
Its role is to expose the FMU as a \syssimx{} component that can be connected, initialized, stepped, and inspected through the common component contract.

The value-reference maps are cached once during construction.
FMI variables are accessed by integer value references rather than by name.
Caching these references allows inputs and outputs to be written and read through batched calls grouped by FMI base type.
This keeps runtime access independent of repeated name lookups.

\paragraph{Direct-Feedthrough Extraction.}
Generic components use perturbation-based feedthrough detection, as described in Section~\ref{sec:impl_component_interface}.
For FMUs, the dependency information is available in the \texttt{ModelStructure} element of \texttt{modelDescription.xml}.
\texttt{FMUComponent} reads this metadata directly and stores it in \texttt{direct\_feedthrough}.
This avoids additional FMI calls and uses the dependency information declared by the FMU exporter.

\subsubsection{Lifecycle Realization}

The wrapper implements the primitive operations of \texttt{CoSimComponent} through FMI~2.0 Co-Simulation calls.
During initialization, it extracts the FMU archive and instantiates the \texttt{FMU2Slave}.
It then calls \texttt{setupExperiment()} and enters initialization mode.
After that, parameters and input start values are applied.
The wrapper finally exits initialization mode.
After the base-class template method returns, the initial outputs are stored in the port states and recorded in the component history.

A time step is delegated to the FMI \texttt{doStep()} call with the current communication point $t$ and the communication step size $dt$.
The base class handles time bookkeeping, output refresh, and history recording around this call.
Output refresh uses the cached value references and reads the FMU outputs through one getter call per active base type.
For \texttt{REAL} outputs, the declared unit is attached before the value is written to the corresponding \texttt{PortState}.

\texttt{evaluate\_outputs(inputs,t)} provides the zero-step output evaluation used by algebraic-loop resolution.
It applies the supplied inputs, evaluates the FMU outputs without advancing the accepted macro time, and returns the resulting output dictionary.
This hook is used only where the FMU supports such zero-step evaluation.
It provides the instantaneous output values needed by Section~\ref{sec:impl_algebraic_loops}.

\subsubsection{State Access and Rollback Boundary}

\texttt{FMUComponent} implements \texttt{get\_state()} and \texttt{set\_state()} as part of the framework's state-transfer interface.
These methods are distinct from native FMI state operations such as \texttt{getFMUState()} and \texttt{setFMUState()}.
\texttt{get\_state()} returns non-\texttt{fixed} and non-\texttt{local} FMU variables with their current values and declared units.
\texttt{set\_state()} uses such a dictionary to re-enter initialization, restore serialized values, and refresh the exposed output ports.

This dictionary state is intended for inspection, state transfer, and re-initialization.
It is not an opaque snapshot of the internal FMU solver state.
The generic \texttt{FMUComponent} therefore does not provide rollback support for the hybrid algorithm.
Rollback for FMU-based hybrid components must be implemented by specialized subclasses when the concrete FMU and solver support it.

\subsubsection{Verification}

The verification of \texttt{FMUComponent} targets the mapping from FMI artefacts to the \texttt{CoSimComponent} contract.
A small purpose-built FMU with two real inputs, two real outputs, one boolean parameter, and a declared feedthrough dependency is used as the test subject.
Table~\ref{tab:fmu_verification} lists the verified properties.
