\subsection{FMI 2.0 Co-Simulation Wrapper}
\label{sec:impl_fmu}

% --- MOTIVATION ---
This subsection describes the implementation of \texttt{FMUComponent} backend wrapper class.
It addresses requirement SR-03-01 (integration of FMI-compliant simulation tools) by mapping FMI 2.0 Co-Simulation FMUs onto the \texttt{CoSimComponent} interface defined in Section~\ref{sec:impl_component_interface}.
The wrapper delegates all interaction with the FMU binary to the \texttt{fmpy} library~\cite{dassault_systemes__catia-systems_fmpy_2026} and encapsulates the FMI 2.0 Co-Simulation lifecycle behind the primitive and hook operations of the component contract.

As introduced in Section~\ref{sec:cosim_fmi}, an FMU in Co-Simulation
mode retains its own internal solver and exposes a standardized set of operators for experiment setup, initialization, stepping, and state access.
The wrapper does not re-implement any of these operators.
Its role is to present an FMU as a \syssimx{} component whose ports, parameters, and direct-feedthrough metadata are derived automatically from the FMU's \texttt{modelDescription.xml} so that the FMU can participate in coupled simulation without manual configuration.

The cached value-reference maps in the last row are a purely local optimization.
The FMI standard addresses variables by integer value references rather than by name, and these references are stable over the lifetime of an FMU instance.
Caching them once per base type allows all subsequent inputs and outputs to be read and written through a single batched call per type, avoiding per-variable lookup overhead during stepping.

\paragraph{Direct-Feedthrough Extraction.}
For generic components, direct feedthrough is detected numerically by output perturbation, as described in Section~\ref{sec:impl_component_interface}.
An FMU, however, declares its input-output dependencies explicitly in the \texttt{ModelStructure} element of the model description.
\texttt{FMUComponent} therefore reads this information directly and populates \texttt{direct\_feedthrough} with the declared dependencies.
This is both more accurate and strictly cheaper than perturbation, since no extra FMI calls are required and the FMU exporter's knowledge of the output equation is authoritative.

\subsubsection*{Lifecycle Realization}

The FMI~2.0 Co-Simulation standard prescribes a state machine whose transitions are triggered by specific operators.
The wrapper realizes this state machine by implementing the primitive and hook operations of \texttt{CoSimComponent} on top of the corresponding \texttt{fmpy} calls.

\paragraph{Initialization.}
\texttt{\_initialize\_component(t0)} executes the six-step sequence required by the standard:
\begin{enumerate}[nosep]
  \item Extract the FMU archive to a temporary directory.
  \item Instantiate an \texttt{FMU2Slave} with the GUID and model identifier taken from the model description.
  \item Call \texttt{setupExperiment(startTime=$t_0$)}.
  \item Enter initialization mode.
  \item Apply parameter start values, then input start values, each batched per base type.
  \item Exit initialization mode.
\end{enumerate}
After the template method \texttt{initialize()} returns, the initial outputs are available in the \texttt{PortState} objects and recorded in the component history (Section~\ref{sec:impl_component_interface}).

\paragraph{Stepping.}
\texttt{\_do\_step\_internal(t, dt)} reduces to a single call to \texttt{doStep(currentCommunicationPoint=$t$, communicationStepSize=$dt$)}.
All surrounding bookkeeping, such as time advancement, output refresh, and history recording, is handled by the template method \texttt{do\_step()} of the base class, so the wrapper itself contributes only the numerical advancement.

\paragraph{Output Refresh.}
\texttt{\_update\_output\_states()} issues one batched FMI getter per base type using the cached output value references and writes the returned values back into the \texttt{PortState} objects.
For \texttt{REAL} outputs, the declared unit is attached so that the port state exposes a Pint quantity rather than a raw float.

\paragraph{Zero-Step Output Evaluation.}
\texttt{evaluate\_outputs(inputs, t)} implements the hook operation introduced in Section~\ref{sec:impl_component_interface}.
It applies the supplied inputs without recording history, issues a \texttt{doStep} with $dt = 0$, and reads the resulting outputs.
This mechanism provides the instantaneous output evaluation required for the algebraic-loop resolution described in Section~\ref{sec:impl_algebraic_loops}.
Zero-step evaluation is admissible under FMI~2.0 Co-Simulation and is preferred over numerical perturbation because it reflects the exact feedthrough behavior declared by the FMU.

\subsubsection*{State Access and Rollback Boundary}

\texttt{FMUComponent} provides \texttt{get\_state()} and \texttt{set\_state()} as part of the generic \syssimx{} state-transfer interface.
These methods must be distinguished from the native FMI state operations exposed by \texttt{fmpy} through methods such as \texttt{getFMUState()} and \texttt{setFMUState()}.
In \syssimx{}, \texttt{get\_state()} returns a dictionary containing non-\texttt{fixed}, non-\texttt{local} FMU variables together with their current values and declared units.
Conversely, \texttt{set\_state()} uses such a dictionary to re-enter the FMU initialization sequence, re-apply serialized parameter and input values, and refresh the exposed output ports.

This dictionary-based state representation is intended for inspection, state transfer, and re-initialization.
It is not an opaque snapshot of the internal FMU solver state.
Consequently, the generic \texttt{FMUComponent} does not provide native rollback support for the hybrid algorithm and does not override \texttt{snapshot\_state()} or \texttt{restore\_state()}.
Rollback for FMU-based hybrid components is implemented only in specialized subclasses when the concrete FMU and solver permit it.

\subsubsection*{Verification}

The verification of \texttt{FMUComponent} targets the mapping from FMI artefacts to the \texttt{CoSimComponent} contract.
A small purpose-built FMU with two real inputs, two real outputs, one boolean parameter, and a declared feedthrough dependency is used as the test subject.
