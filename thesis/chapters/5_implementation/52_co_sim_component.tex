\section{Component Interface}
\label{sec:impl_component_interface}

The \texttt{CoSimComponent} forms the central execution abstraction of \syssimx{}.
It defines the uniform contract through which subsystem models are represented, initialized, advanced in time, and queried for outputs, independent of the concrete backend from which they originate.
In this sense, the \texttt{CoSimComponent} is the common execution interface that allows heterogeneous subsystem models to be orchestrated identically by the system model and the master algorithms.

This abstraction builds on the port system introduced in Section~\ref{sec:impl_port_system}.
While the port system defines how typed and unit-aware interfaces are represented, the \texttt{CoSimComponent} defines how a component behaves at runtime.
It therefore provides the bridge between static interface specification and executable co-simulation behavior.
The following subsection explains its architectural role before the concrete lifecycle semantics are discussed in detail.

\subsection{Architectural Role}

\paragraph{Requirement Mapping.}
The \texttt{CoSimComponent} directly contributes to SR-01-01 and SR-01-02 by representing subsystem models as reusable components with explicit interfaces and by enabling such components to be combined into one system model.
It furthermore supports SR-09-03 and SR-10-01 by exposing a uniform lifecycle and interface contract for all integrated subsystem models, regardless of whether the underlying model originates from an FMI-based tool, a biomechanics environment, a continuum-mechanical solver, or an internal composite model.
Optional extensions of the interface, such as rollback support and event-related hooks, also prepare the abstraction for hybrid behavior in the sense of SR-07-01 and SR-07-02.
Their detailed algorithmic use is discussed later in Section~\ref{sec:impl_hybrid}.

Architecturally, the \texttt{CoSimComponent} occupies the boundary between backend-specific model execution and framework-level orchestration.
Upwards, it presents a stable and backend-independent interface to the \texttt{System} class and to the master algorithms.
Downwards, it encapsulates tool-specific details such as solver setup, model loading, and native stepping calls inside subclass implementations.
This separation is essential for the overall framework design, because it allows system assembly, structural analysis, execution-order computation, and result handling to operate on a common component abstraction rather than on backend-specific runtime objects.

\paragraph{Template-Method Design.}
The \texttt{CoSimComponent} is implemented as an abstract base class following the template method pattern~\cite{GoF}.
In this design, the base class defines the invariant execution sequence of the component lifecycle, while backend-specific subclasses implement the hook methods that realize the actual model behavior.
Public methods such as \texttt{initialize()} and \texttt{do\_step()} therefore establish the framework-controlled lifecycle, whereas protected methods such as \texttt{\_initialize\_component()}, \texttt{\_do\_step\_internal()}, and \texttt{\_update\_output\_states()} are delegated to the concrete subclass.

This design has two consequences. First, generic framework concerns such as port-state management, time bookkeeping, history recording, and capability handling are centralized in the base class.
Second, backend-specific wrappers remain focused on the translation between the common \syssimx{} contract and the concrete simulation tool.
The result is a stable orchestration layer in which heterogeneous components can be scheduled, coupled, and monitored uniformly, even though their internal numerical realization differs substantially.

\paragraph{Mandatory Hooks.}

\subparagraph{Construction.}
Figure~\ref{fig:impl_comp_construction} shows the construction sequence.
The subclass constructor calls the base class constructor, which initializes the internal containers for ports, parameters, and history recording. The subclass then defines its input and output port specifications, describing the component interface in terms of variable names, data types, and physical units.
Port states are created immediately from these specifications so that initial values can be propagated through connections before initialization begins.

\subparagraph{Initialization.}
The initialization sequence is shown in Figure~\ref{fig:impl_comp_initialization}.
The base class exposes a single public \texttt{initialize(t0)} method.
It sets the initial simulation time and then delegates to the abstract \texttt{\_initialize\_component()} hook, where the subclass performs model-specific setup such as loading a solver or configuring internal parameters.
After this hook returns, the base class calls the abstract \texttt{\_update\_output\_states()} hook so that the subclass writes its initial internal state to the output ports.
These initial outputs are recorded and become available to downstream components.

\subparagraph{Simulation Step.}
Figure~\ref{fig:impl_comp_stepping} shows the delegation during a single macro time step.
The algorithm calls \texttt{do\_step(t,\,dt)} on the base class, which delegates the actual computation to \texttt{\_do\_step\_internal()}.
This abstract method advances the internal model state from~$t$ to~$t + dt$.
After the hook returns, the base class updates the component time and invokes \texttt{\_update\_output\_states()} to refresh the output ports with the new state.
The updated values are recorded in the component history for later retrieval.

\subparagraph{Supporting Methods.}
Beyond the three main phases, the base class provides methods for configuration and cleanup.
Component parameters can be modified through \texttt{set\_parameters()} after construction.
The subclass initialization must apply these values when setting up the internal model.
After the simulation loop completes, results are available through the component history, which stores time-stamped output port values with their physical units.
The \texttt{reset()} method restores default parameters and clears the history, enabling re-simulation with a different configuration without reconstructing the component.

This design keeps simple components lightweight.
A basic wrapper only needs to implement the three abstract lifecycle methods.
Components that participate in algebraic loop resolution additionally override \texttt{evaluate\_outputs()} to support zero-step evaluation.
Components that act as event sources implement \texttt{snapshot\_state()} and \texttt{restore\_state()} to enable state rollback for event localization.
The framework detects these capabilities through introspection at initialization time, without requiring explicit capability flags.

\paragraph{State Management.}
The component interface provides two distinct state management mechanisms that serve different purposes:
%
\begin{itemize}[nosep]
  \item \emph{Physical state transfer} 
    (\texttt{get\_state / set\_state}): exports and imports 
    human-readable physical variables (positions, velocities) as 
    named quantities with units. The exported state is interpretable 
    across different model implementations and is used for state 
    transfer during runtime model switching 
    (Section~\ref{sec:impl_multi_model}).
  \item \emph{Rollback state} 
    (\texttt{snapshot\_state / restore\_state}): captures and 
    restores the complete opaque internal state, including 
    solver-specific artifacts. This mechanism is used by the hybrid 
    algorithm to revert components to a previous time during event 
    localization (Section~\ref{sec:impl_hybrid}).
\end{itemize}
%
These two mechanisms are intentionally separate.
A physical state can be adapted and transferred to a different model.
A rollback snapshot does not support this, as it may contain solver-specific data that is meaningless outside the originating component.
