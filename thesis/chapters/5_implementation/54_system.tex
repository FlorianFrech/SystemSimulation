\section{System and Connections}
\label{sec:impl_system}

The \texttt{System} class assembles individual components into a running co-simulation scenario.
It implements the \texttt{System} abstraction introduced in Section~\ref{sec:architecture_system_connections} and realizes \ref{req:SR-03-01} and \ref{req:SR-03-02} under \ref{req:UR-03}.
The event-connection functionality additionally supports \ref{req:SR-04-02} under \ref{req:UR-04}.

Figure~\ref{fig:impl_system_class} gives a class-level overview of the implementation objects involved in system composition and execution.
The structural analysis that derives the execution order from the registered connections is deferred to Section~\ref{sec:impl_structural}, and the master algorithms that consume this order are described in Section~\ref{sec:impl_algorithms}.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsection{System Definition}

A \texttt{System} instance stores the structural definition of a co-simulation scenario.
This includes the registered components, signal connections, event connections, selected algorithm, and aggregated history.
It also tracks the current simulation time and the initialization state.

Components are registered with \texttt{add\_component()} before any connection can reference them.
Registration enforces unique component names within the \texttt{System} instance.
It also rejects additions after \texttt{initialize()} has been called.
This keeps the structural analysis valid for the complete simulation run.
The component history is registered with the system-level \texttt{SystemHistory} instance.
After the simulation, results from all components can therefore be retrieved through one call to \texttt{get\_history()}.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsection{Connection Registration}

\paragraph{Signal Connection.}
A signal connection is represented by an immutable \texttt{Connection} object.
It stores the source component and output port together with the destination component and input port.
The object is frozen and hashable, so it can be used during duplicate checks and graph construction.

Signal connections are registered through \texttt{add\_connection()}.
Before a connection is stored, \texttt{\_validate\_connection()} checks that both components exist, both ports exist, and the port specifications are compatible.
The same validation rejects duplicate connections and enforces single assignment.
A new connection is rejected if another connection already drives the same destination input.
This guarantees a unique source for every consumed input port.

\paragraph{Event Connection.}
Hybrid scenarios use \texttt{EventConnection} to route events from an event source to an event listener.
The source port identifies the event indicator.
The destination port identifies the event input of the event listener.
The zero-crossing direction is defined by the source component and inherited by the generated event subscription.

The \texttt{add\_event\_connection()} method validates the connection and registers the event route.
It also creates the corresponding \texttt{Event} subscription for the event listener.
The subscription is stored on the listener and is consumed by the hybrid algorithm during event dispatch.
Section~\ref{sec:impl_hybrid} describes this dispatch step.
Existing matching subscriptions are reused.
Duplicate event connections are rejected at registration time.

\subsection{Lifecycle Orchestration}

The selected stepping algorithm is stored in the \texttt{algorithm} attribute.
It can be replaced through \texttt{set\_algorithm()}.
A \texttt{GaussSeidelAlgorithm} is installed by default for systems without state events.
At the start of \texttt{initialize()}, the \texttt{System} instance classifies the registered components.
If at least one event source is present, the algorithm is replaced by \texttt{HybridAlgorithm}.
This activates hybrid event handling without requiring manual algorithm selection.

Once all components and connections are registered, the \texttt{System} instance is driven through three phases.

\paragraph{Initialization.}
The \texttt{initialize(t0)} method first classifies the registered components and selects the hybrid algorithm when event sources are present.
It then prepares the component ports, computes direct-feedthrough metadata, and invokes the structural analysis of Section~\ref{sec:impl_structural}.
The resulting execution order initializes the components generation by generation, as shown in Figure~\ref{fig:impl_system_initialization}.
After initialization, the structural definition is fixed for the simulation run.

\paragraph{Run.}
The \texttt{run(t0, tf, dt)} method repeatedly delegates one macro step to the selected algorithm.
The stepping loop advances the time pointer in fixed steps of size \texttt{dt} and clamps the final step to the end time.
Algorithm-specific orchestration is handled by the selected algorithm.
This includes input propagation, algebraic-loop iteration, and event localization (Section~\ref{sec:impl_algorithms}).

\paragraph{Reset.}
The \texttt{reset()} method releases the runtime state of the \texttt{System} instance without removing its structural definition.
It clears the aggregated history and resets all registered components through their own \texttt{reset()} hooks.
It also marks the instance as not initialized.
The registered components, connections, and selected algorithm are retained.
The same scenario can therefore be initialized and executed again without rebuilding the \texttt{System} configuration.

\subsection{Verification}

The verification focuses on the registration contract of the \texttt{System}.
A valid registration must either extend the structural definition or be rejected before simulation state is changed.
The scenario uses lightweight mock components and checks signal connections, event connections, and lifecycle protection.
Table~\ref{tab:system_verification} summarizes the observed behavior.

\begin{table}[t]
  \centering
  \small
  \caption[Registration checks]{Registration checks for signal connections, event connections, and lifecycle protection.}
  \label{tab:system_verification}
  \begin{tabular}{p{3.2cm} p{6cm} p{6cm}}
    \toprule
    \textbf{Verified aspect} & \textbf{Minimal setup} & \textbf{Observed result} \\
    \midrule
    Signal connection registration
      & Three simple feedthrough components are registered.
        A valid connection from \texttt{A.y} to \texttt{C.u} is added.
        A second connection from \texttt{B.y} to the same input \texttt{C.u} is attempted.
      & The first connection is stored.
        The second connection is rejected with a \texttt{ValueError}.
        This confirms that each input port has a unique driver. \\
    \addlinespace

    Event connection registration
      & A hybrid source declares an event indicator.
        A hybrid listener declares a matching event input.
        An \texttt{EventConnection} links the source indicator to the listener input.
      & The event listener receives exactly one matching event subscription.
        The subscription direction is inherited from the source event indicator.
        The connection itself only represents event routing. \\
    \addlinespace

    Lifecycle protection
      & The \texttt{System} instance is initialized after component and connection registration.
        A further component registration is attempted after initialization.
      & Initialization stores the current time and marks the instance as initialized.
        Further component registration is rejected.
        The structural definition is therefore fixed for the simulation run. \\
    \bottomrule
  \end{tabular}
\end{table}

The scenario confirms that the registration contract is enforced uniformly across signal connections, event connections, and lifecycle protection.
The \texttt{System} instance rejects ambiguous or late structural changes before simulation starts.
Event routing is configured through \texttt{EventConnection}, while event semantics remain owned by the source-side event indicator.
Structural-analysis properties are verified separately in Section~\ref{sec:impl_structural}.
