\section{Architectural Overview}
\label{sec:architecture_overview}

Figure~\ref{fig:syssimx_architecture} summarizes the layered architecture of \syssimx{}.
It shows how user code delegates simulation tasks to framework layers and external simulation backends.
The framework contains four internal layers.
The adapter layer maps backend APIs to the component interface.
The core abstraction layer defines components, ports, connections, and multi-model components.
The system-orchestration layer owns the assembled system structure.
The execution layer advances the system through interchangeable algorithms.
The layering follows six design principles:
%
\begin{enumerate}[nosep]
  \item \textit{component-based decomposition}
  \item \textit{tool-agnostic core with backend adapters}
  \item \textit{separation of model and orchestration}
  \item \textit{pluggable execution algorithms}
  \item \textit{explicit and unit-aware interfaces}
  \item \textit{minimal required contract with optional capabilities}
\end{enumerate}
%
The following paragraphs describe the layers from the external tools upward.

\paragraph{External simulation tools.}
External simulation tools provide the backend model representations and numerical solvers.
They include FMI~2.0 Co-Simulation FMUs exported from equation-based modeling environments, OpenSim for musculoskeletal dynamics, and Netgen/NGSolve for finite element analysis.
Each backend provides its own solver, model representation, and programmatic Python interface.
\syssimx{} accesses these backends through their respective APIs.

\paragraph{Adapter layer.}
The adapter layer connects external simulation tools to the common \texttt{CoSimComponent} contract.
Each adapter translates the runtime interface of one backend into framework-level ports, parameters, lifecycle operations, and optional capabilities.
The amount of translation depends on the backend.
FMUs already provide standardized metadata and co-simulation calls.
OpenSim and Netgen/NGSolve require more model-specific wrapper code because their Python APIs expose simulation objects rather than FMI-style descriptors.

This layer keeps the framework core tool-agnostic.
The layers above interact with all backends through the same component contract, while the backend-specific API calls remain inside the adapters.

\paragraph{Core abstractions.}
The core abstraction layer defines the architectural primitives of the framework.
The \texttt{CoSimComponent} base class specifies the contract that every simulation component must satisfy.
This contract includes typed and unit-annotated ports, a lifecycle for initialization and stepping, and optional capabilities for direct feedthrough, event indicators, and rollback.

Component-based decomposition represents a coupled system as interacting components that can be configured and exchanged independently.
The minimal-contract principle keeps simple components lightweight and allows advanced components to expose additional capabilities.
Signal connections and event connections define data flow and event propagation between components.
The \texttt{MultiComponent} abstraction extends the same external interface to several interchangeable models of one physical subsystem.

\paragraph{System orchestration.}
The \texttt{System} class assembles components and connections into a complete co-simulation scenario.
It owns the system-level structure that is shared by initialization, structural analysis, and execution.
Components remain responsible for their internal state integration and output evaluation.
The \texttt{System} abstraction owns the coupling relation between them.

This layer realizes the separation between model behavior and orchestration.
The structural concepts used by this layer are introduced in Section~\ref{sec:233_cosim_structural_analysis}.
Their implementation is described in Chapter~\ref{chap:implementation}.

\paragraph{Execution layer.}
The execution layer contains the master algorithms that advance the coupled system in time.
Each algorithm operates on the same \texttt{System} abstraction and uses the system structure provided by the orchestration layer.
Different algorithms can therefore execute the same system definition without changing the component implementations.
This realizes the principle of pluggable execution algorithms.

\paragraph{Supporting services.}
Supporting services provide unit handling, history recording, and graph-based visualization.
They support model assembly, inspection, and post-processing without changing the component and algorithm contracts.
