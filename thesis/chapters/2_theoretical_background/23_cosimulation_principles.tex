\section{Co-Simulation Principles}
\label{sec:theory_cosim}

Many cyber-physical systems cannot be modeled conveniently within a single tool chain.
Instead, different subsystem models are created in domain-specific environments and later coupled for system-level analysis.
Co-simulation addresses this situation by coordinating several subsystem simulators while preserving their local model representation and numerical solver \cite{gomes_co-simulation_2019-1}.
The present section introduces the terminology and principles that are required for the later architecture and implementation chapters.

\subsection{Terminology}
\label{sec:theory_cosim_terminology}

For the present thesis, it is useful to distinguish clearly between a \emph{monolithic simulation} and a \emph{co-simulation}.
A monolithic simulation solves the coupled system as one global model.
The individual subsystems may still be described in a modular way, but after translation they are handled by one simulation environment and one global numerical problem.
Later in this thesis, the all-Modelica realization of the controlled pendulum serves as such a monolithic reference model.

By contrast, a co-simulation solves the overall system in a \emph{partitioned} form.
Each subsystem remains a separate simulation unit with its own state representation and usually its own solver.
The subsystem simulators exchange coupling variables only at discrete communication points and are coordinated by an external master algorithm or orchestrator \cite{gomes_co-simulation_2019-1}.

This thesis uses the following working definition:
co-simulation is the coordinated execution of two or more coupled subsystem simulators that advance their local states independently between communication points and exchange input and output variables at these points.
The term \emph{partitioned} is preferred here over \emph{distributed modeling}, because the relevant distinction is the structural separation of simulators, not whether the computation is physically distributed across processors or machines.

\subsection{Functional Mock-up Interface and Functional Mock-up Units}
\label{sec:theory_fmi}

The Functional Mock-up Interface (FMI) is the dominant standardized interface for tool-independent model exchange and co-simulation \cite{FMI2.0}.
An exported model that follows this standard is packaged as a \emph{Functional Mock-up Unit} (FMU).
An FMU contains a machine-readable model description, binary code or source code for the exported model, and metadata such as variables, units, and causality information \cite{FMI2.0}.

FMI distinguishes two interface types.
In \emph{Model Exchange}, the FMU provides model equations and callback functions, while the importing environment supplies the numerical solver.
In \emph{Co-Simulation}, the FMU contains its own time integration logic and is advanced by a master through calls such as \texttt{doStep} \cite{FMI2.0}.
This distinction is fundamental.
Model Exchange preserves a single global solver and is therefore closer to the monolithic simulation view, whereas Co-Simulation preserves subsystem-local solvers and fits the partitioned execution considered in this thesis.

For \textit{SysSimX}, FMI is important as a component interface, not as a complete orchestration solution.
The standard defines how an FMU exposes variables and lifecycle operations, but it does not prescribe how several coupled FMUs should be ordered, how algebraic loops should be resolved, or how hybrid events should be handled consistently across subsystem boundaries \cite{gomes_co-simulation_2019-1}.
These orchestration questions remain the responsibility of the master algorithm.

\subsection{Orchestrated Co-Simulation and Communication Steps}
\label{sec:theory_cosim_steps}

In co-simulation, the coupled execution is organized on a communication grid
\begin{equation}
    t_0 < t_1 < \dots < t_k < t_{k+1} < \dots
\end{equation}
with communication step sizes
\begin{equation}
    H_k = t_{k+1} - t_k.
\end{equation}
At each communication point, subsystem outputs are exchanged and the master determines how the next interval is executed.
Between two communication points, each subsystem advances with its own internal solver and may use several internal solver steps that are not visible at the system level \cite{gomes_co-simulation_2019-1,schierz_co-simulation_2012}.

This separation between local integration and global communication is one of the defining features of co-simulation.
The communication step is therefore not identical to the internal solver step.
Within a communication interval, each subsystem usually receives an approximation of its input trajectory derived from the information available at the beginning of the interval.
The simplest case is a piecewise constant input hold, but higher-order extrapolation or iterative correction are also possible \cite{petridis_test_2015,gomes_co-simulation_2019-1}.

The algorithm that coordinates this process is often called the \emph{master algorithm}, \emph{orchestrator}, or \emph{coordinator}.
Its responsibilities include advancing time, triggering subsystem steps, exchanging variables, and enforcing a valid execution order.
The numerical properties of the coupled simulation depend not only on the participating subsystem solvers, but also on the communication step size, the input approximation scheme, and the chosen coupling strategy \cite{gomes_co-simulation_2019-1,sicklinger_interface_2014}.

\subsection{Dependency Analysis and Execution Order}
\label{sec:theory_dependency_analysis}

The interconnection of subsystem inputs and outputs induces a dependency graph.
Whether this graph can be evaluated sequentially depends on the direct-feedthrough properties introduced in Section~\ref{sec:theory_direct_feedthrough}.
If a subsystem output depends directly on its current input, then the corresponding interface relation must be considered when determining the execution order at a communication point.

If the direct-feedthrough dependency graph is acyclic, a valid sequential execution order can be obtained by topological sorting.
This is the basic idea behind dependency analysis in co-simulation.
It determines which components can be evaluated independently, which components must be executed before others, and whether circular instantaneous dependencies are present \cite{broman_requirements_2015}.

Two basic non-iterative coupling patterns are commonly used.
In a \emph{Jacobi-type} scheme, all subsystems start the communication interval from the same previously exchanged data and can therefore be stepped in parallel.
In a \emph{Gauss-Seidel-type} scheme, subsystems are stepped sequentially within the communication point, so later subsystems may already consume outputs that were updated earlier in that same communication cycle \cite{petridis_test_2015}.
Jacobi-type execution offers more parallelism, while Gauss-Seidel-type execution follows one-way dependencies more naturally and may improve accuracy or stability for suitable coupling structures.

\subsection{Algebraic Loops in Coupled Systems}
\label{sec:theory_cosim_algebraic_loops}

If direct-feedthrough dependencies form a closed cycle, no acyclic execution order exists.
The coupled system then contains an \emph{interface algebraic loop}.
This notion is closely related to the algebraic loops introduced in Section~\ref{sec:theory_direct_feedthrough}, but here the loop occurs across subsystem boundaries and therefore directly affects orchestration.

Interface algebraic loops are particularly important in co-simulation because the coupled equations are no longer solved by one monolithic solver.
In a monolithic simulation, algebraic constraints can often be handled within a global nonlinear or differential-algebraic solve.
In co-simulation, however, the solvers are encapsulated inside separate simulation units.
As a result, the master cannot simply propagate signals once through the connection graph, but must either iterate over the coupled interface equations, introduce a tearing strategy, or reformulate the coupling problem \cite{sicklinger_interface_2014,broman_requirements_2015}.

The presence of an algebraic loop is therefore not merely a numerical inconvenience.
It is a structural property of the coupled system that constrains the admissible orchestration strategy.
For the present thesis, this motivates the later separation between structural loop detection and numerical loop resolution in the framework.

\subsection{Hybrid Co-Simulation and Event Handling}
\label{sec:theory_hybrid_cosim}

Many coupled systems are not purely continuous.
Contacts, switching controllers, saturation effects, and mode-dependent subsystem models introduce discrete events in addition to continuous-time evolution.
The hybrid-system concepts introduced in Section~\ref{sec:hybrid_system_representation} therefore also apply at the co-simulation level.

Hybrid co-simulation becomes challenging because events may occur inside a communication interval rather than exactly at a communication point.
If such an event is ignored until the end of the interval, the event time is shifted and the exchanged variables may become causally inconsistent.
For this reason, hybrid co-simulation typically requires event detection, event localization in physical time, and a restart procedure once the event has been processed \cite{broman_determinate_2013,StepRevision_Cremona}.

In addition, several discrete reactions may need to be ordered at the same physical time.
This motivates the use of superdense time semantics, as discussed in the preceding section on hybrid simulation, where the physical event time and the logical ordering of event reactions are distinguished \cite{cremona_hybrid_2019,broman_determinate_2013}.
From the perspective of orchestration, hybrid co-simulation therefore extends ordinary time stepping with rollback, step revision, and ordered event processing.
These mechanisms are fundamental for the later \textit{SysSimX} algorithms, but their concrete implementation is deferred to Chapter~\ref{chap:implementation}.
